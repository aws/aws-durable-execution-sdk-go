### Why each failure is failing (none are silent/unexplained)

- **`1-6`, `3-14`** (custom serdes) — confirmed conformance-suite requirement bug, not an SDK gap. Verified directly against the JS reference SDK's own source and test suite: neither SDK round-trips a custom serdes's transformation back into the top-level handler return value on a fresh execution — both correctly return the raw, untransformed value. These two requirements' own `ExpectedResult.Result` assumes a round-trip that no reference SDK performs.
- **`3-11`** (Child, ReplayChildren mode) — real, unimplemented SDK feature. `types.ContextDetails.ReplayChildren`/`ContextOptions.ReplayChildren` exist on the wire types but are never read or set in `pkg/durable/operations`.
- **`5-1`…`5-16`** (Invoke, all 16) — `ChainedInvokeStartedDetails.DurableExecutionArn` is architecturally only populated for a *durable* invoke target; `conformance/echo-target` is deliberately a plain, non-durable target per this suite's own design intent. Confirmed via the official API reference's own documented field semantics.
- **`8-6,7,8,10,13,17,18` / `9-5,6,7,9,10`** (Parallel/Map completion-policy contract + `MinSuccessful`) — real, fixable SDK gap: this SDK returns a Go error instead of a `BatchResult` when a completion policy is unmet, and `MinSuccessful` isn't wired into the early-exit scheduling loop. Both are cross-cutting (`batch.go` shared by Map and Parallel) and would be a breaking API contract change — deliberately not fixed without a design decision.
- **`1-13`, `8-12`/`9-12`, `9-13`, `9-19`/`9-20`** (not-implemented) — real, scoped, currently-missing features (cross-SDK default retry policy; FLAT nesting mode; custom item namer; whole-result-only serdes), each confirmed via direct code inspection to have no implementation path today.

## 3. Findings surfaced specifically by cross-referencing these three mechanisms

Running all three side by side today surfaced two things neither the example catalog nor the conformance suite would have caught alone:

1. **`large-payload-go`'s cloud integration test failed because its hardcoded function ARN (`:1`) pointed at a stale published Lambda version**, not because of a code regression. `aws lambda list-versions-by-function` showed version `1` was published `2026-07-17T22:44:49`, predating this session's fixes. **Fixed**: published a new version (`:2`) from current `main` and updated the test's hardcoded ARN constant. Re-run confirms this now passes, and `GetError()` correctly surfaces the full, real client-side rejection message for the first time (`docs/remaining-work.md` §13 has the full technical detail).
2. **UPDATE (later session): `completion-config-go`'s "GetDurableExecution top-level fields are nil" finding was itself a staleness bug, not a backend characteristic.** The original investigation's own conclusion — reached via a live probe showing `nil` `Result`/`Error` on both `completion-config-go-example` and the simplest possible `simple-step-go-example` case — was wrong. Direct comparison against the JS reference SDK's own `history-poller.ts` source (prompted by explicit user skepticism: "all other SDKs are working fine, so try to find the issue") led to checking `completion-config-go-example`'s deployed version `:3` directly via its own CloudWatch `DURABLE_OUTPUT` debug log — which showed the OLD, pre-fix wire key (`"ResultPayload"`, not `"Result"`), proving version `:3` was published (2026-07-17) nearly a full day BEFORE the wire-shape fix commit `3c502a8` (2026-07-18) landed, despite an earlier pass believing it was current. Rebuilt and redeployed from current source as version `:4`; a fresh `GetDurableExecution` probe now shows a genuinely populated top-level `Result`. `examples/completion-config-go/cloud_integration_test.go` updated (ARN `:3`→`:4`, real `GetResult`/`GetError` assertions replacing the previous "document the gap" placeholders) and re-verified passing for real. See `docs/remaining-work.md` §13's "FINAL RESOLUTION" for the full evidence trail.

This is a direct example of why cross-referencing all three test mechanisms side by side matters: a green test with a stale deployed function looks identical to a green test against current code until you actually check the deployment timestamp, and a "confirmed backend gap" from six hours earlier turned out to need re-litigating into THREE separate, more precisely-scoped findings once actually re-tested end to end rather than assumed closed by association.
