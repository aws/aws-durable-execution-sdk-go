## 0. ParentID was never populated on ANY checkpointed operation — real correctness bug, fixed this session

**This is significant enough to warrant its own top-level entry, not a footnote — it affected EVERY operation type this SDK produces (Step, Wait, Callback, ChainedInvoke, RunInChildContext, Map/Parallel's MAP_ITERATION/PARALLEL_BRANCH), not just one operation kind.**

### The bug

A user inspecting the real, deployed `examples/completion-config-go` Lambda function's execution history noticed its operations had no `ParentId` populated at all. Investigation confirmed this was NOT a misunderstanding of the API surface: `ParentId` is a real, documented field on **both** `Operation` (the read side, returned by `GetDurableExecutionState`/`GetDurableExecutionHistory`) and `OperationUpdate` (the write side, sent via `CheckpointDurableExecution`) per the official AWS API Reference — "the unique identifier of the parent operation, if this operation is running within a child context." This repo's own `types.OperationUpdate.ParentID`/`types.Operation.ParentID` fields (`pkg/durable/types/wire.go`) already existed, already round-tripped correctly through the in-memory test client (`inmemory_client.go`, `durable_fake_client_test.go`'s `fakeClient`) and the real AWS SDK v2 translation layer (`pkg/durable/awssdk/client.go`'s `toSDKUpdate`/`fromSDKOperation` — both directions confirmed correct, no changes needed there), and were even already correctly documented as unused in `pkg/durable/testing/result.go`'s `GetChildOperations` doc comment (which explicitly said "no operation implementation populates that field... If/when an operation starts populating ParentID explicitly... this can switch to using it directly"). But a grep of all 20 `types.OperationUpdate{}` construction call sites across `pkg/durable/operations/step.go`, `wait.go`, `callback.go`, `invoke.go`, `batch.go`, and `wait_for_condition.go` confirmed **zero** of them ever set `ParentID` — every single checkpoint this SDK has ever sent to the real backend has left the field empty, for every operation kind, since this repo's inception.

Root cause: `pkg/durable/context/dcontext.go`'s `Context.prefix` field already *is* exactly the right value — "this context's step-ID namespace... a child context's prefix is its own step ID within its parent" — but nothing threaded it through to any checkpoint construction site.

Note: this repo's own hierarchical string step IDs (`"1"`, `"1-3"`, etc., as opposed to opaque hashes another SDK might use) are a **separate, and NOT incorrect**, design choice — the API's documented `Id` pattern (`[a-zA-Z0-9-_]+`) is client-assignable and does not mandate a hash. Do not conflate "IDs are plain hierarchical strings" (fine, permitted by the API) with "ParentId is never set" (the actual bug) — they were originally reported together but are independent issues, and only the second is a real defect.

### The fix

Added `dcontext.Context.ParentStepID() string` (returns `c.prefix` — empty for the root context, matching the API doc's "Required: No" for a root-level operation with no parent; the enclosing operation's own step ID for any child context returned by `NewChild`/`NewChildWithName`), and set `ParentID: c.ParentStepID()` on every one of the 20 `types.OperationUpdate{}` literals across all six operation files. Because every operation checkpoints against the exact `*dcontext.Context` value (`c`) it was called on, and `c.prefix` is already correct by construction for that Context (root or child), this required no new state, no new threading of values through function signatures beyond the one-line method call at each existing call site, and no change to `NewChild`/`NewChildWithName` themselves.

Traced through a genuine three-level nested scenario to confirm the fix end-to-end, not just per-call-site in isolation (new test: `TestLocalTestRunner_ParentID_NestedScenario`, `pkg/durable/testing/runner_test.go`): two root-level Steps (`ParentID == ""`), a `RunInChildContext` wrapping one nested Step (the `CONTEXT/RUN_IN_CHILD_CONTEXT` operation itself has `ParentID == ""`; its nested Step's `ParentID` equals the CONTEXT operation's own ID), and a `Parallel` with two branches each running their own Step — confirming a genuine **three-level chain**: the outer `CONTEXT/PARALLEL` operation has `ParentID == ""`, each `CONTEXT/PARALLEL_BRANCH` operation's `ParentID` equals the outer PARALLEL operation's own ID, and each branch's nested Step's `ParentID` equals *that specific branch's own* operation ID (not the outer PARALLEL's ID) — proving the fix correctly derives "parent" from the *immediately* enclosing context at every level, not just the root.

### Read-side (`pkg/durable/testing`): deliberately NOT changed, and why

`TestResult.GetChildOperations` (`pkg/durable/testing/result.go`) still derives parent/child relationships from the hierarchical step-ID-prefix convention rather than consulting `ParentID`, even though `ParentID` is now correctly populated and would work too. This was a deliberate choice (option (a) from this session's own scoping, not option (b)): this is a pure-Go, SDK-internal in-memory test client, not the real backend — the ID-prefix convention is already exactly what determines the real hierarchy for this client (both signals necessarily agree by construction, since a child Context's own prefix IS its enclosing operation's ID), switching would be strictly more code for zero behavioral difference, and `testing.EventSignatures`' `Depth`/`Index` computation plus every existing test predating this fix already depends on the prefix convention. The real fix that mattered is the **outbound wire format** sent to the actual backend — the local test runner's internal correctness was never the bug. `result.go`'s doc comment was updated to reflect this reasoning (it previously, correctly for its time, explained that `ParentID` was unusable because nothing populated it — that explanation is now stale and was rewritten to explain the current, deliberate choice instead). `pkg/durable/execmgr` was checked (grepped for `prefix`/`ParentID`/`HasPrefix`) and confirmed to contain no similar prefix-based derivation logic needing the same treatment or justification.

### Write-side (`pkg/durable/awssdk`): already correct, verified not just assumed

`awssdk/client.go`'s `toSDKUpdate` already translated `u.ParentID` into the real AWS SDK v2's `lambdatypes.OperationUpdate.ParentId` (guarded with `if u.ParentID != ""`, so an empty ParentID — a root-level operation — correctly omits the field rather than sending an empty string), and `fromSDKOperation` already translated `op.ParentId` back into `types.Operation.ParentID` in the read direction. Both directions were read and confirmed correct as part of this session; no changes were needed to this file.

## 0b. Operation IDs were plain hierarchical strings, never hashed — real gap vs. all three reference SDKs, fixed this session

**This is similarly foundational to §0's ParentID fix, and directly builds on it — a bug in the SAME area of the codebase (`dcontext.Context`'s ID generation), found by the same kind of direct cross-SDK source comparison that found §0's bug, not speculation.**

### The bug

This Go SDK's `context.Context.NextStepID()`/`PeekStepID()` minted and checkpointed PLAIN hierarchical string IDs — `"1"`, `"1-3"`, `"1-3-1"` — as the real `Id`/`ParentId` values sent to the actual backend. Direct source reads of all three reference SDKs this session (TypeScript, Python, Java — via `raw.githubusercontent.com`) confirmed every one of them hashes operation IDs before ever exposing them; none uses a plain, structurally-revealing string as its real, wire-visible `Id`. The most concrete, fully-verified reference is Java's `OperationIdGenerator` (`sdk/src/main/java/software/amazon/lambda/durable/execution/OperationIdGenerator.java`):

```java
public String nextOperationId() {
    var counter = String.valueOf(operationCounter.incrementAndGet());
    return hashOperationId(operationIdPrefix + counter);  // SHA-256, full hex digest
}
```

An earlier session's own writeup (§0 above) had explicitly flagged this as a *separate, not-incorrect* design choice ("this repo's hierarchical string step IDs... are a separate, and NOT incorrect, design choice — the API's documented Id pattern (`[a-zA-Z0-9-_]+`) is client-assignable and does not mandate a hash"). That framing was accurate about the API's own permissiveness (a plain string IS a valid `Id` per the wire contract) but incomplete about what "matching the reference SDKs" actually requires: the API tolerating a plain string does not mean the reference SDKs actually send one, and this session's direct source reads confirm all three deliberately choose not to, for reasons (not asserted here, since only the mechanism — hash instead of plain string — was verified, not the reference SDKs' own stated rationale) that plausibly include not leaking the handler's own control-flow structure (nesting depth, branch/iteration counts, retry counts) into an externally-visible identifier.

### Design decision: match Java's exact scheme, not JS's, not Python's, not a fourth compromise

JS, Python, and Java each hash operation IDs with **different** algorithms/encodings from one another (confirmed by reading all three SDKs' actual source this session) — they do not agree on one canonical scheme. This Go SDK picks Java's as its **one** reference point rather than attempting to reconcile three mutually-inconsistent schemes into a fourth: SHA-256, full 64-character lowercase-hex digest, no truncation, hashing input `contextId + "-" + counter` (or just `counter` if `contextId` is empty), computed **immediately at ID-generation time** — the raw, unhashed value never escapes the ID generator, unlike JS's own approach (confirmed by reading its source), which defers hashing to checkpoint-send time instead. Nothing about this choice is wire-visible to a caller of ANY SDK reading back this Go SDK's own checkpointed history: the backend treats `Id`/`ParentId` as opaque caller-assigned strings matching `[a-zA-Z0-9-_]+` regardless of which SDK produced them, so there is no cross-SDK ID-*compatibility* requirement to satisfy here — only "hash instead of exposing a plain string," and Java's own concrete scheme is as good a canonical choice as any of the three for a Go-native scaffold with no prior committed ID-format contract of its own to preserve.

### The fix

`context.Context.NextStepID()`/`PeekStepID()` (`pkg/durable/context/dcontext.go`) now return `SHA-256(hashInputPrefix(prefix) + counter)` — the full 64-hex-char digest — instead of the plain `prefix + "-" + counter` string. `hashInputPrefix` mirrors Java's exact `contextId != null ? contextId + "-" : ""` null-check logic (Go's empty-string zero value stands in for Java's `null`). Two additional, non-obvious pieces had to change correctly for this to compose across nesting levels without corrupting anything:

- **The root Context's hash-input prefix is the EXECUTION operation's own ID** — a backend-assigned, dynamically-generated value (confirmed UUID-like from a live invocation, predating this task), **not** something this SDK's own counter mints — matching Java's own documented "for root contexts the prefix is the EXECUTION operation ID." `dcontext.NewRoot` gained a new `rootOperationID` parameter for this, threaded from `durable.go`'s `executionOp.ID` (which required reordering `WithDurableExecution`'s existing `findExecutionOperation` lookup to run *before* `NewRoot` is called, since the lookup's result is now a required input to it, not just consumed afterward).
- **`Context.prefix` (the hash-input) and the real `ParentID` to checkpoint are now two DELIBERATELY separate fields** (`prefix` and the new `parentID`), where before this task they were always the same value. This is a real bug this task's own design would otherwise have introduced: the root Context's `prefix` is now the EXECUTION operation's own ID (non-empty), but a root-level operation must still report an EMPTY `ParentID` (per §0's own established semantics — a root-level operation has no parent) — conflating the two fields would have wrongly reported the EXECUTION operation's ID as the `ParentId` of every root-level `Step`/`Wait`/`Context` operation. `Context.ParentStepID()` (added in §0) now returns the new `parentID` field, not `prefix`; `NewChild` sets both `prefix` and `parentID` to the same already-hashed `parentStepID` argument (correct for a child context, where the two really do coincide, per Java's own "no additional hashing for ParentId itself, only for generating a NEW id" rule).

Every one of the 20 `types.OperationUpdate{}`/`ParentID: c.ParentStepID()` call sites across `step.go`/`wait.go`/`callback.go`/`invoke.go`/`batch.go`/`wait_for_condition.go` required **no changes at all** — they already just use `c.NextStepID()`'s return value and `c.ParentStepID()` directly, both of which now transparently return hashes instead of plain strings from the exact same call shape.

### `pkg/durable/testing`: a forced redesign, not optional, once IDs are opaque

Two places in the local test runner derived parent/child hierarchy and golden-file `Depth`/`Index` ordering by **string-parsing** the hierarchical ID (checking `"1-1"` is prefixed by `"1"` plus a `"-"` separator) — an approach that is not merely suboptimal but **impossible** once IDs are opaque SHA-256 hashes (a hash reveals nothing about the string it was computed from):

- **`testing/result.go`'s `GetChildOperations`** now walks `Operation.ParentID` directly (`op.ParentID == parentID`) instead of ID-string-prefix matching. This is strictly simpler than the code it replaced, and was already possible in principle since §0 populated `ParentID` correctly — the earlier session had deliberately kept the ID-prefix convention for this specific method as a documented, lower-risk choice, reasoning the two signals "necessarily agree by construction" for this in-memory client. Hashing breaks that equivalence for real: the two signals no longer agree (the prefix signal simply stops working), forcing the switch this session made.
- **`testing/signature.go`'s `EventSignatures`** (golden-file `Depth`/`Index` computation) needed a two-part redesign: **Depth** now comes from walking the `ParentID` chain (straightforward, mirroring `GetChildOperations`). **Index** (a sibling's position, e.g. "the 2nd branch") is harder, since a hash carries no numeric "this was checkpoint N" signal the way a plain ID's trailing counter segment did. The fix adds `dcontext.MintOrder(id)` — a small, process-global registry `context.Context.NextStepID()` itself stamps at ID-**mint** time (not checkpoint-arrival time — see the concurrency pitfall below), recording the order in which every hashed ID was ever produced. `EventSignatures` sorts each depth level's siblings by this mint order, which is proven to produce IDENTICAL `Index` values to the pre-hashing derivation, since mint order and the old counter-order signal are the exact same event, just observed two different ways. For a `CloudTestRunner` result (a real backend's own IDs, never minted by this process at all), this falls back to `Operation.StartTimestamp` ordering, then to input order — matching this function's own pre-existing, honestly-documented "not confirmed to matter in practice" fallback philosophy for cloud-observed operations that don't follow this SDK's own minting convention.
- **A real concurrency bug was found and fixed while building this**, deterministically reproducible (not a `-race` flake): an earlier draft stamped the ordinal at **checkpoint-arrival** time instead of mint time (in `testing/inmemory_client.go`'s `Checkpoint` method). `Map`/`Parallel`'s `runBatch` (`batch.go`) already claims every branch/item's step ID **deterministically, by index**, on the single parent goroutine before spawning any branch goroutine — a pre-existing production correctness requirement (see `batch.go`'s own bug #3 writeup, predating this task) with nothing to do with hashing. But each branch's *checkpoint* is still enqueued later, from **inside** that branch's own concurrently-running goroutine — so checkpoint **arrival** order is NOT guaranteed to match mint/index order under real goroutine scheduling, even though mint order always is. This was caught immediately, not hypothetically: `examples/map-parallel-go`'s own pre-existing golden-file test (`TestHandler_EmptyOrderBatch`) failed with two `PARALLEL_BRANCH` siblings' checkpoints legitimately arriving out of index order, reproducing on essentially every run. Fixing this required moving the ordinal-stamping into `NextStepID()` itself (mint time, always deterministic) rather than patching the arrival-time approach further — confirmed stable across 20+ repeated runs of both `Map`/`Parallel` examples after the fix.
- **`testing/inmemory_client.go`** needed no changes beyond what the `EventSignatures` redesign already required elsewhere (an earlier draft's now-reverted checkpoint-arrival-time sequencing lived here briefly — see above) — it already round-tripped `ParentID` correctly (§0), and operation IDs are used as opaque map keys throughout, which works identically whether the key is a short plain string or a 64-character hash.
- **`pkg/durable/execmgr`** was re-checked (grepped for `prefix`/`HasPrefix`/ID-string-parsing) and confirmed to contain no similar derivation logic — consistent with §0's own prior finding for the same package.

### Golden files: confirmed NOT to need regeneration, and why

`EventSignatures`' own output format — `{Depth, Index, Type, SubType, Status, Name}` — deliberately excludes raw IDs by design (predating this task; see `signature.go`'s own doc comment). Confirmed by re-running every existing example's test suite (all 11 modules, `-race -count=20`) that every committed `testdata/*.history.json` golden file still matches byte-for-byte with ZERO regeneration: `git status`/`git diff` on every `testdata/` path shows no changes across this entire session. This confirms the redesigned `Depth`/`Index` derivation (ParentID-chain-walking plus mint-order sorting) produces the IDENTICAL numeric values the old ID-string-parsing derivation did — only the *mechanism* changed, not any golden file's *content* — exactly as predicted before implementing the fix, and empirically confirmed after.

### Test-file fallout: hardcoded plain-string ID assertions, fixed

## 0c. `WaitForCondition` RETRY checkpoint rejected by the real backend, PLUS a second, independent bug (`READY` status never handled) it exposed — both fixed this session

**Similarly foundational to §0/§0b — this affects `WaitForCondition` for every deployment, not just the one example that surfaced it, and unlike most of this document's other real-bug writeups, this one required a genuine live-deployment failure AND a second live-deployment failure (after the first fix) to fully uncover, because the two bugs masked each other's absence of local coverage.**

### Bug #1 (the one that failed loudly): RETRY checkpoint sent both `Payload` and `Error`, which the real backend rejects outright

Deploying `examples/map-with-condition-and-callback-go` (version 1, the original, never-before-deployed code for this brand-new example) to a real Lambda function (`map-with-condition-and-callback-go-example`, account `730758745077`, `us-east-1`) and invoking it with `{"orderIds":["order-1","order-2","order-3"],"carrierPollOrderId":"order-2"}` produced a genuine checkpoint API failure from the REAL backend, visible in the function's own `DURABLE_OUTPUT` CloudWatch log line:

```
checkpointing retry: checkpoint API error (NON_RETRYABLE): awssdk.Client.Checkpoint: operation error Lambda: CheckpointDurableExecution, https response error StatusCode: 400, ... InvalidParameterValueException: Cannot provide both an Error and Payload for RETRY action.
```

**Root cause**, confirmed by reading the actual source: `pkg/durable/operations/wait_for_condition.go`'s `pollAndCheckpoint` checkpointed a RETRY action with BOTH `Payload: &serialized` (the current poll state, needed so the poll loop can recover it on the next invocation) AND `Error: opErr` (a sentinel representing "condition not met," reusing the same wire slot a genuine checkFn error would use) in the SAME `types.OperationUpdate`. The real backend rejects this combination outright, for RETRY specifically. This is NOT how `Step`'s own RETRY checkpoint works (`step.go`'s `retryOrFail` sends ONLY `Error`, never `Payload` — a plain `Step` has no state to carry between retries, so it never hit this) — but `WaitForCondition`'s whole design DOES need to carry poll state forward across a RETRY (`checkFn` takes the last state as input on the next poll), so simply dropping `Payload` (the "conservative fallback" this task's own instructions anticipated might be necessary) would have silently broken the operation's entire reason for existing.

**The real fix, confirmed with high confidence via three independent sources, not guessed:**

1. **Official AWS API Reference** (`docs.aws.amazon.com/lambda/latest/api/API_OperationUpdate.html`, re-fetched this session): `Payload`'s doc reads "The payload for **successful** operations" — i.e. Payload's documented purpose is scoped to success, not general state-carrying, which is a hint but not on its own a confirmed mechanism for what to do instead on RETRY.
2. **All three reference SDKs' actual source**, read directly this session (not paraphrased from memory or docs):
   - **TypeScript** (`packages/aws-durable-execution-sdk-js/src/handlers/wait-for-condition-handler/wait-for-condition-handler.ts`): its RETRY-equivalent checkpoint call is `{Action: RETRY, Payload: serializedState, StepOptions: {...}}` — **no `Error` field at all**.
   - **Python** (`packages/aws-durable-execution-sdk-python/src/aws_durable_execution_sdk_python/operation/wait_for_condition.py`): `OperationUpdate.create_wait_for_condition_retry(identifier=..., payload=serialized_state, next_attempt_delay_seconds=delay_seconds)` — **no `error` parameter**.
   - **Java** (`sdk/src/main/java/software/amazon/lambda/durable/operation/WaitForConditionOperation.java`): `OperationUpdate.builder().action(RETRY).payload(serializedState.serialized()).stepOptions(...)` — **no `.error(...)` call**.
   
   All three reference SDKs — independently, in three different languages — never set `Error` on a WaitForCondition RETRY checkpoint. "Condition not yet met" is never modeled as an `Error` at the wire level for this operation; only a genuine `checkFn` exception is (and that correctly checkpoints FAIL with `Error` set, no `Payload`, matching `Step`'s own FAIL path).
3. **The real backend's own error message**: "Cannot provide both an Error and Payload for RETRY action" is precisely consistent with reading #2 as the confirmed mechanism, not a coincidence.

**The fix**: `wait_for_condition.go`'s RETRY checkpoint now sends `Payload` only (dropping `Error`) — the mirror image of `Step`'s own RETRY checkpoint (`Error` only, no `Payload`), each operation sending exactly the one field it actually needs. The terminal FAIL checkpoint was ALSO changed to drop `Payload` (keeping only `Error`), matching the same three reference SDKs' FAIL-equivalent checkpoints (none of which send a payload alongside the error either) — this second change was not independently confirmed to be REJECTED by the real backend the way RETRY+Payload+Error was, but sending it would deviate from every reference SDK's own established behavior for no confirmed benefit, and the state is inherently moot once the operation has terminally failed (there is no further poll attempt to seed with it). **No capability was given up**: `Payload` still carries the poll state forward on every RETRY, exactly as before, just without the `Error` field that the real backend rejects — the fix removes a redundant, rejected field, not the state-carrying mechanism itself.

**Confidence: very high.** This is not a single-source guess — three independently-implemented reference SDKs in three different languages agree exactly, the official API doc's wording is consistent with it, and the fix was re-verified end-to-end against the real backend after applying it (see the real-cloud re-verification section below), producing zero `InvalidParameterValueException` occurrences across a full poll-to-completion run.

### Bug #2 (the one only visible AFTER fixing bug #1): `types.OperationStatusReady` was never handled by `WaitForCondition`'s (or `Step`'s) replay-lookup switch

After deploying the bug #1 fix and re-invoking against the real backend, the `InvalidParameterValueException` was gone — but the execution never progressed past the first poll attempt's `pollCount`, looping every 5 seconds for the full 300-second `ExecutionTimeout` before being killed by `TIMED_OUT`, with every single poll's log line reading `pollCount:1, status:pending`, `attempt:1` — i.e. the poll state was silently resetting to the caller's `initialState` on every single re-invocation, even though `StepDetails.Attempt` (the RETRY bookkeeping) WAS correctly incrementing checkpoint-side.

**Root cause**: `runWaitForCondition`'s replay-lookup `switch existing.Status` only had cases for `Succeeded`/`Failed`/`Pending` — but the real backend does NOT re-invoke with the operation still checkpointed as `PENDING` once a poll delay elapses; it flips the operation to `types.OperationStatusReady` (`"READY"` — the eighth `OperationStatus` value, added in an earlier session per that session's own writeup elsewhere in this document, but never consumed by any operation's control flow until now) and re-invokes with THAT status. `READY` fell through the switch entirely (no case matched it) and hit the function's own bottom-of-function fallback — `pollAndCheckpoint(c, stepID, name, checkFn, initialState, cfg, 0)` — silently restarting the poll loop from scratch on every single fresh invocation. `step.go`'s structurally identical switch has the EXACT same gap, but it is invisible there: a plain `Step` has no carried state to lose when it silently "restarts" (`executeAndCheckpoint`'s fallback just re-runs `fn` fresh regardless of the attempt number it's handed), so nothing about `Step`'s own behavior depends on `READY` being handled correctly. `WaitForCondition`'s carried poll state is what makes this bug's effect observable at all.

**Why local tests never caught this, and why they will now**: `pkg/durable/testing/inmemory_client.go`'s `inMemoryClient` (the `checkpoint.Client` `LocalTestRunner` uses) and `pkg/durable/durable_fake_client_test.go`'s `fakeClient` (used by `pkg/durable`'s own direct tests) BOTH modeled a RETRY-checkpointed operation's `SkipTime`-driven "delay elapsed" transition as `PENDING`, never `READY` — so every existing local test, including `wait-for-condition-go`'s and this new example's own dedicated tests, only ever exercised the `PENDING` case, which WAS handled correctly, and never touched the missing `READY` case at all. Fixed by changing `inMemoryClient`'s `skipTime`-driven RETRY handling to set `types.OperationStatusReady` (matching the real, now-confirmed backend behavior) instead of `types.OperationStatusPending`. Including any of these would make a "golden file" fail on every single run through no real behavior change at all, defeating the whole point. `Depth`/`Index` (new relative to the JS reference's flatter `{type, subType, status, name}` tuple) capture STRUCTURE — nesting and sibling ordering — deterministically derived by walking each operation's own hierarchical ID string (splitting on `-`, sorting each depth level's siblings numerically by their trailing counter segment) rather than relying on any Go map iteration order, since `TestResult.operations` is a `map[string]types.Operation` (see `result.go`) that Go gives zero ordering guarantees over — unlike the JS reference SDK's own naturally insertion-ordered array, which needs no equivalent reconstruction. The root `EXECUTION` operation is excluded entirely: it's not something the handler's own code chose to run, and its `{EXECUTION, "", status, ""}` entry would add zero diagnostic value to every single golden file.

### Real SDK bugs found and fixed (7 total, all independently re-verified before and after)

1. **`Step`'s `AtLeastOncePerRetry` semantics never checkpointed `STEP/START` at all** (only `AtMostOncePerRetry` did) — every other operation kind already checkpointed START unconditionally; fixed by removing the conditional gate in `step.go`.
2. **Every `SubType` value the SDK ever checkpointed was wrong**: several operations omitted `SubType` entirely (`json:"SubType,omitempty"` meant the key was absent from the wire, not just empty), and every place that did set one used SCREAMING_SNAKE_CASE (`WAIT_FOR_CONDITION`, `RUN_IN_CHILD_CONTEXT`, etc.) instead of the PascalCase (`WaitForCondition`, `RunInChildContext`, etc.) both the conformance suite and the real Java reference SDK expect. Confirmed the real backend echoes back exactly whatever string this SDK sends, verbatim — the casing bug was entirely this SDK's own doing. Fixed via a new canonical constant block in `operations/errors.go` and every checkpoint call site across `step.go`/`wait.go`/`callback.go`/`invoke.go`/`batch.go`/`wait_for_condition.go`.
3. **Every checkpointed operation failure omitted `ErrorType` entirely** (`json:"ErrorType,omitempty"` again meant an absent key, not an empty one) — fixed via a new `checkpointErrorObject(err)` helper (`errors.go`) that derives `ErrorType` via `fmt.Sprintf("%T", err)`, used at all 5 real call sites. This alone moved 5 Step-suite requirements from FAILED to PASSED.
4. **A crashed `AtLeastOncePerRetry` step's resume path unconditionally re-sent `STEP/START`** even though the step was already `STARTED` from the prior (crashed) invocation — the real backend genuinely rejects a second START on an already-STARTED step (`InvalidParameterValueException: "Invalid current STEP state to start."`). Fixed by splitting `step.go`'s single execute-and-checkpoint function into a fresh-attempt path (`executeAndCheckpoint`, sends START) and a resume path (`executeResume`, does not) sharing a common outcome-checkpointing tail. The identical class of bug was **proactively** fixed the same way in `WaitForCondition` (`wait_for_condition.go`) once its own missing-START bug (below) was fixed and would otherwise have introduced this exact regression on its own crash-resume path.
5. **`WaitForCondition`'s poll loop never checkpointed `STEP/START` at all**, for any attempt — the sole operation kind in the package with this gap. Because the zero-option default retry strategy is `NoRetry()`, every `WaitForCondition` call with no explicit retry strategy failed immediately on its first poll. Fixed with the same `executeAndCheckpoint`/`executeResume`-style split as finding 4.
6. **`WaitForCallback` had three real, distinct configuration/behavior gaps**, all pure wiring gaps rather than missing backend features: `WithWaitForCallbackTimeout` was accepted but silently discarded (its own doc literally said "NOT YET IMPLEMENTED"); no heartbeat-timeout option existed at all (`WithWaitForCallbackHeartbeatTimeout` added); the internal submitter step accepted no retry configuration (`WithWaitForCallbackSubmitterRetryStrategy` added). All three fixed by wiring `WaitForCallback`'s own config through to `CreateCallback`'s/`Step`'s already-working lower-level options. A fourth, related bug in the same area: `deserializeCallbackResult` treated a legitimate payload-less external callback success as an error, rather than returning the zero value.
7. **`finishBatch` (shared by `Map` and `Parallel`) serialized the outer `BatchResult` wrapper with the caller's per-item custom serdes**, which is documented and reasonably implemented to handle a single item value, not the wrapper struct — while the read side (`deserializeBatchResult`) already correctly used plain JSON unconditionally. Fixed by having the write side match the read side: always plain `encoding/json` for the outer wrapper, never the per-item serdes.

Also fixed along the way (not conformance-suite-driven, found via general repo hygiene during this initiative): `execmgr` terminal-status handling for `Invoke` (already documented above in this file's own history) remained correct throughout; no additional unrelated regressions were introduced.

### Still-open, non-SDK-fixable gaps (the two dominant causes of the 104 FAILED count)

These are backend/architectural findings, not client-side bugs — nothing in this Go SDK's own code can close either one unilaterally.

1. **`GetDurableExecution`'s own top-level `Result` field is never populated for a genuinely completed execution**, even though `GetDurableExecutionHistory`'s event-level `Result.Payload` fields (`StepSucceededDetails`, `ContextSucceededDetails`, etc.) are correctly populated everywhere they belong. Confirmed via a direct, real `GetDurableExecution` call against a live completed execution, independent of both this SDK and the conformance tool's own tooling. This is, by a wide margin, **the single largest cause of FAILED results in this whole initiative** — the overwhelming majority of the 104 FAILED requirements fail on this exact field alone, with an otherwise byte-for-byte-correct event history (individually spot-checked, suite by suite, throughout this initiative).
2. **`ExecutionFailedDetails.Error.Payload` comes back completely empty** (`{"Truncated": false}`, no `ErrorMessage`/`ErrorType`) for any execution that fails via an uncaught callback failure/timeout, or via a Map/Parallel batch's own aggregate failure — `ExecutionStatus` itself (FAILED) is always correct, only the nested `Error.Payload` is missing. Two real, distinct remediation attempts were made and both independently confirmed NOT to close this (see the Callback-suite writeup below for the full detail): adding a client-side `ErrorType` field to the output object made no observed difference, and routing FAILED outputs through the Lambda Runtime API's `/error` endpoint instead of `/response` made things *worse* (the backend then treated it as a retryable invocation-level crash instead of a terminal durable-execution failure).

A third, narrower architectural finding was discovered in the Parallel/Map suites and is **not** classified as a NotImplemented gap (see below for why) but is worth calling out here: this SDK's `Map`/`Parallel` completion-policy contract diverges from what the conformance suite expects. Every reference SDK models "did this batch meet its configured `CompletionConfig` policy" as a field ON the returned batch result object for the caller to inspect/rethrow, entirely separate from whether the outer batch operation's own checkpoint succeeded. This Go SDK instead lets `batchCompletion.overallSucceeded`'s result directly drive `ContextSucceeded` vs. `ContextFailed`, returning a Go error instead of a result value whenever the policy is unmet. Confirmed via real deployments (Parallel's `8-6` fail-fast scenario shows `ContextFailed` where `ContextSucceeded` was expected; `8-9`, where the policy is NOT exceeded, correctly shows `ContextSucceeded` — isolating the mismatch to the policy-unmet case specifically). A related, smaller finding: `CompletionConfig.MinSuccessful` is not actually an early-exit gate in this SDK today — only `ToleratedFailureCount`/`ToleratedFailurePercentage` stop the scheduling loop early; `MinSuccessful` is only consulted after every branch/item has already run to completion (confirmed via Parallel's `8-8` and Map's `9-7`, both showing all branches/items running despite a `MinSuccessful` threshold that should have stopped things early). Both findings affect Map and Parallel equally (they share `batch.go`) and were deliberately not fixed — a foundational contract change with cross-cutting impact on every existing caller of `Map`/`Parallel` (including `examples/completion-config-go` and this SDK's own `batch_test.go` coverage), out of scope for a single conformance suite's own stage.

## 12. Correction to Section 11: the "backend gaps" were this SDK's own bugs

**Prompted by a direct, correct user challenge**: "I don't believe it - all other SDKs like Java, Python and TypeScript work perfectly, all integ tests there are passing. do an investigation to find out what did we miss." That challenge was right. Section 11 above, written immediately after Stage 9, concluded that the top-level `GetDurableExecution.Result` field and `ExecutionFailedDetails.Error.Payload` were confirmed, non-SDK-fixable backend limitations. **They were not.** Both were real, mechanical bugs in this SDK's own Runtime API response wire format, found by directly comparing this SDK's `types.DurableExecutionOutput` against the JS reference SDK's own real, tested source (`with-durable-execution.ts`/`core.ts`) rather than continuing to trust an earlier session's own unconfirmed conclusion.

### What was actually wrong

1. **Success path**: this SDK sent the wire key `"ResultPayload"`. The real, correct key (confirmed against the JS SDK's own passing test assertions) is `"Result"`. The backend silently discarded the unrecognized key — no error, just never populated — which is exactly why `GetDurableExecution.Result` appeared permanently empty across every one of the 9 conformance suites in Section 11.
2. **Failure path**: this SDK sent two flat top-level fields, `"ErrorMessage"`/`"ErrorType"`. The real, correct shape is a single nested `"Error"` object (`{Status: FAILED, Error: {ErrorMessage, ErrorType, ...}}`). Same silent-discard mechanism, same root cause — this is exactly why `ExecutionFailedDetails.Error.Payload` came back empty for every uncaught callback/batch failure documented in Section 11, despite two separate remediation attempts during that section's own investigation.
3. **A third, smaller, related bug** surfaced only once fix #2 above let the error message actually populate: `operations.OperationError`'s own internal Go-debugging decoration (e.g. `callback "x" (id y): not approved`) was leaking into the wire-level `ErrorMessage`, when the correct value is the bare, original message (`not approved`) the external system/business logic actually produced. Fixed via a new, narrow `OperationError.Cause()` accessor and a `durable.go` helper that uses it — see that helper's own doc comment for two prior, wrong approaches that were tried and self-caught (by this repo's own example-module tests) before landing on the correct one.

All three fixes are in `pkg/durable/types/wire.go` and `pkg/durable/durable.go` (plus a small addition to `pkg/durable/operations/errors.go`), committed separately from every Stage 0-8 commit, touching zero handler files.

### Real-world impact

A full 148-requirement re-run (same harness, same account, region `us-east-1`) went from **37 passed / 104 failed** (Section 11's own final numbers) to **111 passed / 31 failed** (0 optional-failed, 6 not-implemented unchanged). The overwhelming majority of this entire initiative's "explained" failures were two wrong JSON keys.

### Corrections to Section 11's specific claims

## 18. `1-6`/`3-14`/`5-16` were NOT conformance-suite bugs after all — the fresh-execution serdes round-trip was a real, systematic SDK bug (fixed), plus one real handler bug

**CORRECTION of §16's and §17's own repeated "all three confirmed conformance-suite bugs" conclusion**, per direct user feedback that another team member's independent Go implementation passes 100% of the conformance suite — which is logically incompatible with these three requirements being suite bugs, and prompted a re-investigation that proved the earlier conclusion wrong.

**What the earlier investigation got wrong**: §16 claimed, of `1-6`/`3-14`, "confirmed this matches the JS reference SDK's own identical behavior (its `step-handler.ts` only deserializes on an already-succeeded replay path, never a fresh execution)." That reading of `step-handler.ts` was simply incorrect. The JS reference SDK's fresh-execution success path is, verbatim in structure: `safeSerialize(serdes, result)` → checkpoint → **`return await safeDeserialize(serdes, serializedResult)`** — it ALWAYS returns the serdes round-trip, never the raw in-memory value. `run-in-child-context-handler.ts` even documents this explicitly: "the value handed back from a child context has always passed through the serdes round-trip, regardless of payload size" — with the same round-trip on its large-payload/ReplayChildren re-execution and virtual-context paths. `wait-for-condition-handler.ts` likewise returns its own `deserializedState` (and even feeds the round-tripped state to the wait strategy). Map/Parallel items execute through the child-context handler and inherit the same guarantee.

**The real bug (SDK, 4 sites)**: this Go SDK's fresh-execution success paths all returned the raw in-memory value — `step.go`'s `executeAndCheckpoint` (`return result, nil`), `invoke.go`'s `RunInChildContext` (both the small-payload and ReplayChildren branches, plus `replayChildrenResult`'s re-execution path), `batch.go`'s `runBatchItem`, and `wait_for_condition.go`'s `checkAndCheckpointOutcome`. With any TRANSFORMING serdes (the suite's uppercasing one; equally a compressing/encrypting/pointer-indirecting one), this made the same operation return two DIFFERENT values depending on whether the current invocation executed it (raw value) or replayed it (checkpoint's deserialized value) — a genuine determinism violation, not just a conformance mismatch. Fixed via a shared `roundTripSerialized[T]` helper (`pkg/durable/operations/serdes_roundtrip.go`) applied at all 4 sites, using the same any→T JSON-fallback conversion `deserializeStepResult`/`deserializeContextResult` already use on their replay paths. `Invoke` itself needed no SDK change (its result only ever arrives via the replay deserialize path, which was already correct).

**The real bug (conformance handler, 1 site)**: `5-16` was NOT a YAML authoring bug either. §16 reasoned the doubly-quoted `ExpectedResult.Result: '"HELLO"'` could not be intentional — it is: the requirement's custom result deserializer receives the RAW checkpointed payload `"hello"` (JSON quotes included) and uppercases it VERBATIM to `"HELLO"` (quotes now literal string content), which the top-level default serdes JSON-encodes as `'"\"HELLO\""'` — one `json.loads` of that is exactly the expected 7-character quoted string. Our handler (`conformance/handlers/invoke_5_16.go`) json-unmarshalled the payload BEFORE uppercasing, producing the bare `HELLO`. Fixed by uppercasing the raw pointer as-is.

**New tests**: `pkg/durable/durable_serdes_roundtrip_test.go` — per-site fresh-path round-trip tests (Step, RunInChildContext, Map items, WaitForCondition, all with an uppercasing serdes mirroring `1-6`/`3-14`'s own), plus `TestStep_FreshAndReplayReturnSameValue` pinning the determinism property directly (fresh and replay invocations of the same step must observe the identical transformed value).

**Verification**: root build/vet/gofmt clean; full root `go test ./... -race -count=1` passes (all pre-existing tests unaffected — the default JSON serdes round-trips to an equal value, so only a transforming serdes observes the change); conformance module builds/vets clean; insight module tests pass; all 26 examples build/test clean.
